Introdução

Nesta demonstração, vamos mostrar como migrar entre dois clusters Amazon EKS de versoes diferentes sem nenhum downtime, usando uma abordagem blue/green com GitOps (ArgoCD) e Route53 weighted routing.

CenárioImagine que você tem um cluster EKS na versão 1.34 (duas versoes atras). O upgrade in-place de control plane e uma "one-way door" - não existe rollback. E se fosse um EKS on Outposts Local Cluster v1, nem existiria o botao de upgrade pra v2. A solução: não vamos atualizar o cluster velho. Vamos substituir ele sem que o usuário perceba.

O que você vai ver

  • Dois clusters (1.34 e 1.36) coexistindo na mesma VPC, sincronizando o mesmo repositorio Git
  • Tráfego migrando progressivamente (90/10 → 50/50 → 0/100) via pesos no DNS - controlados por commits no Git
  • Rollback instantâneo (um commit reverte tudo em menos de 2 minutos)
  • O cluster velho sendo destruido sem que nenhum request falhe

Componentes

ComponentePapel
Amazon EKS (1.34 + 1.36)Clusters blue e green
ArgoCD (self-managed)GitOps - sincroniza o mesmo repo em ambos os clusters
Route53 (weighted records)Distribui tráfego entre os clusters por peso
ExternalDNSReconcilia automaticamente os pesos do Git no Route53
KarpenterProvisiona nodes sob demanda em ambos clusters
Gitea (HTTPS)Repositorio GitOps auto-hospedado (long-lived)

Arquitetura

A chave da solução: o ambiente (VPC, DNS, repositorio Git) sobrevive; os clusters são descartaveis.

Mecanismo de shiftO peso vive em um arquivo YAML no repositorio Git (ingress-weight.yaml). Editar o peso, commitar e dar push e TUDO que precisa ser feito. ArgoCD sincroniza, ExternalDNS atualiza o Route53. Auditavel no git log, reversivel com git revert.
CamadaConteudoCiclo de vida
core-infraVPC, hosted zone, GiteaPermanente - sobrevive a toda migração
eks-blueCluster EKS 1.34 + ArgoCDDescartavel - destruido no final
eks-greenCluster EKS 1.36 + ArgoCDVira o novo baseline

1. Estado Atual (Blue) 5 min

Vamos explorar o ambiente atual - um cluster EKS 1.34 servindo 100% do tráfego.

Verificar a versão do cluster

kubectl --context eks-blue version | grep Server
Server Version: v1.34.x-eks-...

Nodes do cluster (MNG core + Karpenter workload)

kubectl --context eks-blue get nodes -L role,karpenter.sh/nodepool
2 nodes "core" (MNG, t3.large) + 1-2 nodes Karpenter (spot, workload)

Aplicação rodando

kubectl --context eks-blue get pods -n demo -o wide
3 pods demo-app nos nodes Karpenter

Registro weighted no Route53

aws route53 list-resource-record-sets --hosted-zone-id $ZONE_ID \
  --query "ResourceRecordSets[?Name=='app.bluegreen.lab.'].[SetIdentifier,Weight]" \
  --output table
eks-blue | 100 (100% do tráfego no blue)

Testar o app (de dentro da VPC)

kubectl --context eks-blue run test --rm -i --restart=Never \
  --image=python:3.13-slim -- python3 -c "
import json, urllib.request
r = json.load(urllib.request.urlopen('http://app.bluegreen.lab/'))
print(json.dumps(r, indent=2))"
{"cluster": "eks-blue", "message": "hello from the eks-blue cluster"}
Ponto-chave para o clienteEste cluster está 2 versoes atras. O upgrade in-place de control plane EKS não tem rollback. Em Outposts Local Clusters v1, nem existe botao de upgrade pra v2. Vamos resolver dos dois jeitos: não atualizar, e sim SUBSTITUIR - sem que o usuário perceba.

2. Novo Cluster (Green) 5 min

O cluster GREEN (EKS 1.36) ja está provisionado, com o MESMO app sincronizado do MESMO repositorio Git. Vamos validar que está funcional - sem receber nenhum tráfego real.

Versão do green

kubectl --context eks-green version | grep Server
Server Version: v1.36.x-eks-...

App rodando no green

kubectl --context eks-green get pods -n demo -o wide
3 pods demo-app Running (mesmo deploy, mesmo Git - cluster diferente)

Diferenca entre os dois stacks (Terraform)

diff terraform/eks-blue/main.tf terraform/eks-green/main.tf
~6 linhas diferentes: nome, versão, tags. Mesmo modulo. Clusters são gado.

Validar que o green responde (sem tocar no DNS)

kubectl --context eks-green run test --rm -i --restart=Never \
  --image=python:3.13-slim -- python3 -c "
import json, urllib.request
r = json.load(urllib.request.urlopen('http://demo-app.demo.svc/'))
print(json.dumps(r, indent=2))"
{"cluster": "eks-green", "message": "hello from the eks-green cluster"}
Ponto-chaveO cluster novo está 100% funcional - mesma aplicação, mesmo repo Git, validado de ponta a ponta. E o usuário final nem sabe que ele existe. Weight 0. Zero risco ate aqui.

3. Shift de Tráfego 15 min

Agora vamos migrar o tráfego progressivamente. O mecanismo: editar o peso no Git, commitar, e deixar o GitOps fazer o resto.

Como funcionaNenhum comando toca o Route53 diretamente. O peso vive em ingress-weight.yaml no repositorio Git. ArgoCD sincroniza a annotation no Ingress, ExternalDNS reconcilia o Route53. Tudo auditavel via git log.

Iniciar o watch de tráfego (manter em terminal separado)

kubectl --context eks-blue run traffic-watch --rm -i --restart=Never \
  --image=python:3.13-slim -- python3 -uc "
import json, urllib.request, collections, time
tally = collections.Counter()
while True:
    try:
        r = json.load(urllib.request.urlopen('http://app.bluegreen.lab/', timeout=3))
        c = r['cluster']; tally[c] += 1; total = sum(tally.values())
        dist = ' | '.join(f'{k}: {v} ({100*v//total}%)' for k,v in sorted(tally.items()))
        color = '\033[34m' if 'blue' in c else '\033[32m'
        print(f'{color}{c:10s}\033[0m [{dist}]')
    except: pass
    time.sleep(1)"
100% das respostas vem do eks-blue (inicio)

Shift para 90/10 (canary)

# Editar os pesos no Git
git clone $GITEA_REPO /tmp/shift && cd /tmp/shift
# Blue: 100 -> 90
sed -i 's/aws-weight: "100"/aws-weight: "90"/' gitops/apps/demo-app/overlays/blue/ingress-weight.yaml
# Green: 0 -> 10
sed -i 's/aws-weight: "0"/aws-weight: "10"/' gitops/apps/demo-app/overlays/green/ingress-weight.yaml
git add -A && git commit -m "shift: blue=90 green=10" && git push
Após ~1-2 min, o watch mostra ~10% das respostas vindas do eks-green

Shift para 50/50

sed -i 's/aws-weight: "90"/aws-weight: "50"/' gitops/apps/demo-app/overlays/blue/ingress-weight.yaml
sed -i 's/aws-weight: "10"/aws-weight: "50"/' gitops/apps/demo-app/overlays/green/ingress-weight.yaml
git add -A && git commit -m "shift: blue=50 green=50" && git push
Watch mostra distribuicao ~50/50 entre blue e green

Shift para 0/100 (cutover completo)

sed -i 's/aws-weight: "50"/aws-weight: "0"/' gitops/apps/demo-app/overlays/blue/ingress-weight.yaml
sed -i 's/aws-weight: "50"/aws-weight: "100"/' gitops/apps/demo-app/overlays/green/ingress-weight.yaml
git add -A && git commit -m "shift: blue=0 green=100 (cutover)" && git push
100% no green. O blue continua vivo como rede de seguranca.
Ponto-chaveToda a migração aconteceu via commits no Git. Sem comandos no Route53, sem scripts, sem automacao obscura. O git log E o audit trail. E o cluster velho segue de pe - pronto pra receber tráfego de volta se algo der errado.

4. Rollback 5 min

O argumento que fecha: se algo der errado, quanto tempo leva pra voltar?

Cronometrem.

# Um commit reverte TUDO
sed -i 's/aws-weight: "0"/aws-weight: "100"/' gitops/apps/demo-app/overlays/blue/ingress-weight.yaml
sed -i 's/aws-weight: "100"/aws-weight: "0"/' gitops/apps/demo-app/overlays/green/ingress-weight.yaml
git add -A && git commit -m "ROLLBACK: blue=100 green=0" && git push
Watch volta a mostrar 100% eks-blue em menos de 2 minutos
Compare com a alternativa
  • Upgrade in-place: rollback = restaurar backup do etcd + downtime. Horas, não minutos.
  • Outposts Local Clusters v1->v2: não existe upgrade, e o "rollback" seria re-provisionar o v1. Dias.
  • Blue/green: um commit. O estado anterior CONTINUA EXISTINDO. Não e um plano de rollback, e um fato.

5. Decommission do Blue 5 min

Após confirmar que o green está estavel (soak period em produção), destruimos o blue.

Verificar que o green tem 100% do tráfego

aws route53 list-resource-record-sets --hosted-zone-id $ZONE_ID \
  --query "ResourceRecordSets[?Name=='app.bluegreen.lab.'].[SetIdentifier,Weight]" --output table
eks-green | 100

Destruir o cluster blue

cd terraform/eks-blue && terraform destroy
Watch continua mostrando 100% green SEM NENHUM ERRO durante a destruicao
Ponto-chaveO cluster velho não existe mais. O usuário nunca percebeu. No Outposts, este e o momento em que o hardware do Local Cluster v1 e liberado pro v2. E o green agora e o novo "blue" - na proxima versão, repetimos o mesmo playbook. Upgrade virou processo, não projeto.

6. Argo Rollouts (bonus) 10 min

Mesma filosofia, outra altitude: progressive delivery dentro do cluster (canary de pods).

Duas altitudes
  • Entre clusters: Route53 weighted (o que acabamos de ver) - migração de versão do cluster
  • Dentro do cluster: Argo Rollouts canary - deploy de novas versoes do app no dia-a-dia

Iniciar um canary (nova versão do app)

kubectl argo rollouts set image rollouts-demo rollouts-demo=argoproj/rollouts-demo:green -n demo
25% dos pods migram pra nova versão e o rollout PAUSA esperando aprovacao

Dashboard visual

kubectl argo rollouts get rollout rollouts-demo -n demo --watch

Aprovar o canary (promote)

kubectl argo rollouts promote rollouts-demo -n demo
Rollout progride: 25% -> 50% -> 100% (com pausa de 30s entre etapas)
Ponto-chaveCom AnalysisTemplates conectados no Prometheus ou CloudWatch, o promote vira automático baseado em metricas. E o mesmo racional da migração de cluster aplicado a TODO deploy de sexta-feira.

7. Kargo Pipeline (bonus) 15 min

Transforma o shift manual (commits no Git) num pipeline governado: Freight flui por estagios com gates de aprovacao + verificacao automática.

Kargo vs Argo Rollouts
Argo RolloutsKargo
EscopoPods dentro de um clusterPromocao entre estagios (clusters/ambientes) via Git
Nesta demoCanary de release no greenPipeline: canary(10%) -> half(50%) -> cutover(100%)
RelacaoComplementares - Kargo usa AnalysisTemplates do Rollouts como verificacao

Visualizar o pipeline

kubectl -n bluegreen-migration get stages
3 Stages: canary, half, cutover

Promover para o primeiro estagio (canary: 10%)

kargo promote --project bluegreen-migration --freight $FREIGHT --stage canary
Kargo clona o repo, edita os pesos (blue=90, green=10), commita, da push. O ArgoCD sincroniza. Verificacao roda (probe HTTP 200). Status: Succeeded.

Avancar: half (50%) e cutover (100%)

kargo promote --project bluegreen-migration --freight $FREIGHT --stage half
# Aguardar verificacao...
kargo promote --project bluegreen-migration --freight $FREIGHT --stage cutover
O Freight so avanca quando o estagio anterior e verificado com sucesso (gate automático)
Ponto-chaveE o mesmo git commit de antes, mas agora com governanca: aprovacao humana ou automática, verificacao entre estagios, audit trail no Kargo. Escala pra frota de clusters e ambientes.

Conclusão e Próximos Passos

O que demonstramos

  • Migração zero-downtime entre clusters EKS via blue/green + GitOps
  • Rollback em menos de 2 minutos (um commit)
  • O cluster velho e a rede de seguranca ate ser destruido
  • Progressive delivery em duas altitudes (Rollouts + Kargo)

Como isso se aplica ao seu cenário

Se você precisa...Este pattern resolve porque...
Upgrade de versão EKS sem riscoO cluster novo e validado a frio; rollback e instantâneo
Migrar de Outposts Local Clusters v1 -> v2Não existe upgrade in-place; este E o playbook
Mudar de MNG pra Karpenter / Auto ModeO green nasce com a config nova; o blue morre com a velha
Governanca de promocao entre ambientesKargo orquestra com gates + verificacao automática
