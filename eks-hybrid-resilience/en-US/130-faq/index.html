    F.A.Q

    What about persistent storage? Our stateful workloads?

    Stateful works on Hybrid Nodes - what does not work is EBS (tied to the AZ, and the EBS CSI is not on the list of compatible add-ons). Local options:

    • hostPath - simple, tied to the node (it is how the official GPU burst sample  persists LLM models locally)
    • local PersistentVolumes with nodeAffinity
    • third-party CSI - Longhorn, Ceph, OpenEBS, or the CSI of the DC's own storage array
    • FSx CSI is on the compatible list, but it is network storage that depends on the region (fails on disconnect)

    Action: validate with the customer's storage team which CSI their array offers. Ref: compatible add-ons .

    What about observability DURING the disconnect? Do we go blind?

    Metrics/logs to CloudWatch/AMP stop flowing during the disconnect (regional dependency). Mitigations:

    • Secondary local backend: on-prem Prometheus + ADOT with dual-exporter (this is what Phase 7 demonstrates)
    • crictl for local troubleshooting without a control plane
    • On the AWS side: a CloudWatch alarm on NodeNotReady (control plane logs) detects the disconnect

    Ref: best practices - network disconnections .

    Does a pod that CRASHES during the disconnect restart?

    Yes - unlike a node restart (Scenario 4). The kubelet manages restartPolicy locally, without the API server, as long as the image is in the containerd cache. Production prerequisites:

    • Pre-pull of the critical images on all nodes
    • containerd GC with discard_unpacked_layers=false (do not discard images)

    And if the disconnect lasts more than 12 hours?

    The pods keep running regardless of an expired credential - it only affects node↔AWS communication, not the local workload. About the credentials:

    • SSM Hybrid Activation: 1h credential; stops renewing offline (reconnection may take up to 30 min of backoff - a systemctl restart of the agent forces it)
    • IAM Roles Anywhere: configurable up to 12h, reconnection in seconds

    For long windows: IRA with a high durationSeconds. Ref: host credentials .

    Our IDP uses admission webhooks (policy engines). What happens?

    Important production gotcha: if a webhook backend runs on the hybrid nodes and the DC disconnects, the API server cannot reach it.

    • With failurePolicy: Fail, this blocks operations on the ENTIRE cluster (not just on-prem)
    • Recommendations: run critical webhooks on cloud nodes, or use failurePolicy: Ignore + replicas on both sides
    • Action: review the platform's webhooks (Kyverno/OPA/Gatekeeper) against this criterion

    And cloud bursting?

    Demonstrated in Phase 6 (overflow) and can evolve to Karpenter + Spot triggered by KEDA/Prometheus. Note: bursting depends on connectivity to the region - it is complementary to resilience (one uses the cloud when it is there, the other survives when it is not).

    Doesn't DNS become a single point of failure on disconnect?

    It does, if CoreDNS runs only in the cloud - it was a finding of this lab (Phase 4b - DNS Resiliency):

    • Internal names (*.svc.cluster.local): require CoreDNS. Validated fix: CoreDNS on each node + internalTrafficPolicy: Local (pre-baked). internalTrafficPolicy: Local is the critical point - it makes each pod use its own node's CoreDNS. Topology hints are not reliable in a small cluster; with Cilium, NodeLocal DNSCache requires a Local Redirect Policy (optional cache layer)
    • Public names: the Route 53 data plane is global (100% SLA) - but if the DC resolves via a Resolver endpoint in the VPC (regional, over the private link), that path dies with the disconnect. A local resolver in the DC for public names
    • The local CoreDNS serves from cache even without the API server - existing names resolve offline

    Two datacenters: a single cluster or one per DC?

    Recommendation: one cluster per DC (smaller blast radius, independent upgrades, lower latency). If they opt for a single cluster with nodes in both DCs:

    • Mandatory zone labels (topology.kubernetes.io/zone per DC) - Kubernetes cancels evictions when an ENTIRE zone becomes unreachable, protecting each DC
    • Network requirement: up to 200ms RTT and 100Mbps+ per DC
