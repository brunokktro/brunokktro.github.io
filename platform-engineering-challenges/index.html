Desafio 1: Networking Stack com kro + ACK

Objetivo

Criar um ResourceGraphDefinition (RGD) do kro que provisiona uma stack completa de networking na AWS usando ACK (AWS Controllers for Kubernetes).

Contexto

O kro permite criar abstrações de alto nível que orquestram múltiplos recursos AWS. Neste desafio, você criará uma VPC com 3 subnets em diferentes AZs e um Security Group.

Requisitos

  • VPC com CIDR 192.168.0.0/16
  • 3 Subnets públicas em AZs diferentes (us-west-2a, us-west-2b, us-west-2c)
  • Security Group associado à VPC
  • Status exportado com IDs dos recursos criados

Desafio

Crie um RGD chamado NetworkingStack que aceite um parâmetro name e provisione toda a infraestrutura de rede. O status deve expor os IDs da VPC, subnets e security group.

Dica: Use o ACK EC2 controller com recursos VPC, Subnet e SecurityGroup.

💡 Ver solução

Solução

apiVersion: kro.run/v1alpha1
kind: ResourceGraphDefinition
metadata:
  name: networkingstack.kro.run
spec:
  schema:
    apiVersion: v1alpha1
    kind: NetworkingStack
    spec:
      name: string
    status:
      networkingInfo:
        vpcID: ${vpc.status.vpcID}
        subnetAZA: ${subnetAZA.status.subnetID}
        subnetAZB: ${subnetAZB.status.subnetID}
        subnetAZC: ${subnetAZC.status.subnetID}
        securityGroup: ${securityGroup.status.id}
  
  resources:
    - id: vpc
      template:
        apiVersion: ec2.services.k8s.aws/v1alpha1
        kind: VPC
        metadata:
          name: vpc-${schema.spec.name}
        spec:
          cidrBlocks:
            - 192.168.0.0/16
          enableDNSHostnames: false
          enableDNSSupport: true
    
    - id: subnetAZA
      template:
        apiVersion: ec2.services.k8s.aws/v1alpha1
        kind: Subnet
        metadata:
          name: subnet-a-${schema.spec.name}
        spec:
          availabilityZone: us-west-2a
          cidrBlock: 192.168.0.0/18
          vpcID: ${vpc.status.vpcID}
    
    - id: subnetAZB
      template:
        apiVersion: ec2.services.k8s.aws/v1alpha1
        kind: Subnet
        metadata:
          name: subnet-b-${schema.spec.name}
        spec:
          availabilityZone: us-west-2b
          cidrBlock: 192.168.64.0/18
          vpcID: ${vpc.status.vpcID}
    
    - id: subnetAZC
      template:
        apiVersion: ec2.services.k8s.aws/v1alpha1
        kind: Subnet
        metadata:
          name: subnet-c-${schema.spec.name}
        spec:
          availabilityZone: us-west-2c
          cidrBlock: 192.168.128.0/18
          vpcID: ${vpc.status.vpcID}
    
    - id: securityGroup
      template:
        apiVersion: ec2.services.k8s.aws/v1alpha1
        kind: SecurityGroup
        metadata:
          name: cluster-security-group-${schema.spec.name}
        spec:
          vpcID: ${vpc.status.vpcID}
          name: my-sg-${schema.spec.name}
          description: Security group for networking stack

Como usar

# Aplicar o RGD
kubectl apply -f networking-stack.yaml

# Criar uma instância
cat <<EOF | kubectl apply -f -
apiVersion: v1alpha1
kind: NetworkingStack
metadata:
  name: my-app
spec:
  name: my-app
EOF

# Verificar status
kubectl get networkingstack my-app -o yaml

Conceitos-chave

  • ResourceGraphDefinition: Define uma nova API customizada
  • Schema interpolation: ${vpc.status.vpcID} referencia outputs de outros recursos
  • Dependency management: kro gerencia automaticamente a ordem de criação
  • Status propagation: Informações dos recursos AWS são expostas no status

Próximos Passos

  • Adicionar Internet Gateway e Route Tables
  • Parametrizar CIDRs e AZs
  • Adicionar NAT Gateways para subnets privadas

Desafio 2: Pod com RDS usando kro + ACK

Objetivo

Criar um RGD que provisiona um Pod Kubernetes conectado a uma instância RDS PostgreSQL, com as credenciais injetadas automaticamente.

Contexto

Platform Engineers precisam abstrair a complexidade de conectar aplicações a bancos de dados gerenciados. Com kro + ACK, você pode criar uma API simples que provisiona tanto o banco quanto a aplicação.

Requisitos

  • RDS DBInstance PostgreSQL (db.t3.micro, 20GB)
  • Pod com imagem customizável
  • Variável de ambiente POSTGRES_ENDPOINT injetada automaticamente
  • Parâmetros: applicationName, image, location

Desafio

Crie um RGD chamado DeploymentAndAWSPostgres que aceite nome da aplicação e imagem Docker, e provisione o banco + pod com conexão configurada.

Dica: Use interpolação ${dbinstance.status.endpoint.address} para injetar o endpoint.

💡 Ver solução

Solução

apiVersion: kro.run/v1alpha1
kind: ResourceGraphDefinition
metadata:
  name: deploymentandawspostgres
spec:
  schema:
    apiVersion: v1alpha1
    kind: DeploymentAndAWSPostgres
    spec:
      applicationName: string
      image: string
      location: string

  resources:
    - id: dbinstance
      template:
        apiVersion: rds.services.k8s.aws/v1alpha1
        kind: DBInstance
        metadata:
          name: ${schema.spec.applicationName}-dbinstance
        spec:
          engine: postgres
          dbInstanceIdentifier: ${schema.spec.applicationName}-dbinstance
          allocatedStorage: 20
          dbInstanceClass: db.t3.micro
          masterUsername: admin
          masterUserPassword:
            name: ${schema.spec.applicationName}-db-secret
            key: password

    - id: pod
      template:
        apiVersion: v1
        kind: Pod
        metadata:
          name: ${schema.spec.applicationName}-pod
        spec:
          containers:
            - name: app
              image: ${schema.spec.image}
              env:
                - name: POSTGRES_ENDPOINT
                  value: ${dbinstance.status.endpoint.address}
                - name: POSTGRES_PORT
                  value: ${dbinstance.status.endpoint.port}
                - name: POSTGRES_USER
                  value: admin
                - name: POSTGRES_PASSWORD
                  valueFrom:
                    secretKeyRef:
                      name: ${schema.spec.applicationName}-db-secret
                      key: password

Pré-requisitos

Criar secret com senha do banco:

kubectl create secret generic my-app-db-secret \
  --from-literal=password='SuaSenhaSegura123!'

Como usar

# Aplicar o RGD
kubectl apply -f deployment-postgres.yaml

# Criar aplicação com banco
cat <<EOF | kubectl apply -f -
apiVersion: v1alpha1
kind: DeploymentAndAWSPostgres
metadata:
  name: my-app
spec:
  applicationName: my-app
  image: postgres:15-alpine
  location: us-east-1
EOF

# Verificar recursos criados
kubectl get dbinstance
kubectl get pod my-app-pod

# Ver logs do pod
kubectl logs my-app-pod

Conceitos-chave

  • Cross-resource dependencies: Pod aguarda RDS estar pronto
  • Status interpolation: Endpoint do RDS injetado automaticamente
  • Secret management: Credenciais gerenciadas via Kubernetes Secrets
  • Declarative infrastructure: Tudo definido em YAML

Melhorias possíveis

  • Usar Deployment ao invés de Pod
  • Adicionar readiness probe que testa conexão com banco
  • Criar DBSubnetGroup para controlar placement
  • Adicionar backup retention e maintenance window

Próximos Passos

  • Adicionar connection pooling (RDS Proxy)
  • Implementar read replicas
  • Configurar automated backups

Desafio 3: VPC Composition com Crossplane

Objetivo

Criar uma Composition do Crossplane que provisiona uma VPC completa com subnets públicas e privadas em múltiplas AZs.

Contexto

Crossplane Compositions permitem criar abstrações reutilizáveis de infraestrutura. Diferente do kro (focado em Kubernetes-native), Crossplane é mais voltado para infraestrutura cloud-agnostic.

Requisitos

  • VPC com CIDR configurável
  • 3 subnets públicas (mapPublicIpOnLaunch: true)
  • 3 subnets privadas
  • Tags Kubernetes para ELB (kubernetes.io/role/elb)
  • PatchSets para parâmetros comuns (region, providerConfig)

Desafio

Crie uma Composition que aceite parâmetros de VPC e subnets, e provisione toda a infraestrutura usando o Crossplane AWS Provider.

Dica: Use FromCompositeFieldPath patches e patchSets para evitar repetição.

💡 Ver solução

Solução (resumida)

apiVersion: apiextensions.crossplane.io/v1
kind: Composition
metadata:
  name: xvpcsubnets.network.awsblueprints.io
  labels:
    awsblueprints.io/provider: aws
    crossplane.io/xrd: xvpcsubnets.network.awsblueprints.io
spec:
  writeConnectionSecretsToNamespace: crossplane-system
  compositeTypeRef:
    apiVersion: network.awsblueprints.io/v1alpha1
    kind: XVpcSubnet

  patchSets:
    - name: common-parameters
      patches:
        - type: FromCompositeFieldPath
          fromFieldPath: spec.resourceConfig.providerConfigName
          toFieldPath: spec.providerConfigRef.name
        - type: FromCompositeFieldPath
          fromFieldPath: spec.resourceConfig.region
          toFieldPath: spec.forProvider.region

  resources:
    - name: vpc
      base:
        apiVersion: ec2.aws.crossplane.io/v1beta1
        kind: VPC
        spec:
          forProvider:
            enableDnsSupport: true
            enableDnsHostNames: true
            tags:
              - key: Name
      patches:
        - type: PatchSet
          patchSetName: common-parameters
        - type: FromCompositeFieldPath
          fromFieldPath: spec.parameters.vpc-cidrBlock
          toFieldPath: spec.forProvider.cidrBlock
        - type: FromCompositeFieldPath
          fromFieldPath: spec.parameters.vpc-Name
          toFieldPath: spec.forProvider.tags[0].value

    - name: public-subnet1
      base:
        apiVersion: ec2.aws.crossplane.io/v1beta1
        kind: Subnet
        metadata:
          labels:
            type: subnet
            visibility: public
        spec:
          forProvider:
            mapPublicIpOnLaunch: true
            vpcIdSelector:
              matchControllerRef: true
            tags:
              - key: Name
              - key: kubernetes.io/role/elb
                value: "1"
      patches:
        - type: PatchSet
          patchSetName: common-parameters
        - type: FromCompositeFieldPath
          fromFieldPath: spec.parameters.vpc-Name
          toFieldPath: spec.forProvider.tags[0].value
          transforms:
            - type: string
              string:
                fmt: 'public-subnet1-%s'
        - type: FromCompositeFieldPath
          fromFieldPath: spec.parameters.publicSubnet1-cidrBlock
          toFieldPath: spec.forProvider.cidrBlock
        - type: FromCompositeFieldPath
          fromFieldPath: spec.parameters.publicSubnet1-availabilityZone
          toFieldPath: spec.forProvider.availabilityZone

    - name: private-subnet1
      base:
        apiVersion: ec2.aws.crossplane.io/v1beta1
        kind: Subnet
        metadata:
          labels:
            type: subnet
            visibility: private
        spec:
          forProvider:
            mapPublicIpOnLaunch: false
            vpcIdSelector:
              matchControllerRef: true
            tags:
              - key: Name
              - key: kubernetes.io/role/internal-elb
                value: "1"
      patches:
        - type: PatchSet
          patchSetName: common-parameters
        - type: FromCompositeFieldPath
          fromFieldPath: spec.parameters.vpc-Name
          toFieldPath: spec.forProvider.tags[0].value
          transforms:
            - type: string
              string:
                fmt: 'private-subnet1-%s'
        - type: FromCompositeFieldPath
          fromFieldPath: spec.parameters.privateSubnet1-cidrBlock
          toFieldPath: spec.forProvider.cidrBlock

CompositeResourceDefinition (XRD)

Desafio 4: IAM Capability Role para ArgoCD

Objetivo

Criar a IAM Role necessária para habilitar o ArgoCD como EKS Capability, seguindo o princípio de least-privilege.

Contexto

O ArgoCD EKS Capability não roda nos seus worker nodes - ele roda no control plane gerenciado pela AWS. Para isso, a AWS precisa assumir uma role na sua conta. Essa role é chamada de IAM Capability Role e é o ponto de entrada de segurança de toda a integração.

Diferente de uma role comum, ela usa um service principal específico: capabilities.eks.amazonaws.com. Sem a trust policy correta, o ArgoCD simplesmente não consegue ser habilitado no cluster.

Além da trust policy, as permissões da role determinam o que o ArgoCD pode acessar: repositórios no CodeCommit, segredos no Secrets Manager, charts no ECR. O princípio é conceder apenas o que for necessário para o seu caso de uso.

Requisitos

  • Trust policy com o service principal capabilities.eks.amazonaws.com
  • Permissão para leitura de um repositório específico no CodeCommit (não wildcard)
  • Permissão para leitura de segredos no Secrets Manager (usar a managed policy correta)
  • Permissão para pull de charts no ECR

Desafio

Crie a IAM Role ArgoCD-Capability-Role com as permissões mínimas descritas acima. Em seguida, habilite o ArgoCD Capability no seu cluster EKS usando essa role.

Dica: A trust policy precisa do sts:AssumeRole para o service principal correto. Consulte a documentação de segurança das EKS Capabilities para o formato exato.

💡 Ver solução

Solução

1. Trust Policy

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Service": "capabilities.eks.amazonaws.com"
      },
      "Action": "sts:AssumeRole"
    }
  ]
}

2. Criar a role

aws iam create-role \
  --role-name ArgoCD-Capability-Role \
  --assume-role-policy-document file://trust-policy.json

3. Permissão CodeCommit (repositório específico)

aws iam put-role-policy \
  --role-name ArgoCD-Capability-Role \
  --policy-name CodeCommitAccess \
  --policy-document '{
    "Version": "2012-10-17",
    "Statement": [{
      "Effect": "Allow",
      "Action": "codecommit:GitPull",
      "Resource": "arn:aws:codecommit:us-east-1:ACCOUNT_ID:meu-repo"
    }]
  }'

4. Permissão Secrets Manager

aws iam attach-role-policy \
  --role-name ArgoCD-Capability-Role \
  --policy-arn arn:aws:iam::aws:policy/AWSSecretsManagerClientReadOnlyAccess

5. Permissão ECR

aws iam attach-role-policy \
  --role-name ArgoCD-Capability-Role \
  --policy-arn arn:aws:iam::aws:policy/AmazonEC2ContainerRegistryPullOnly

6. Habilitar ArgoCD Capability no cluster

aws eks create-addon \
  --cluster-name meu-cluster \
  --addon-name argocd \
  --service-account-role-arn arn:aws:iam::ACCOUNT_ID:role/ArgoCD-Capability-Role

O que acontece por baixo

Quando você cria a Capability, a AWS automaticamente:

  • Instala os CRDs do ArgoCD no cluster (Application, ApplicationSet, AppProject)
  • Cria um Access Entry para a role com as policies AmazonEKSArgoCDClusterPolicy e AmazonEKSArgoCDPolicy
  • Disponibiliza a UI do ArgoCD via EKS Console em Clusters > Capabilities > Argo CD

Validação

# Verificar status da capability
aws eks describe-addon --cluster-name meu-cluster --addon-name argocd \
  --query 'addon.status'

# Verificar CRDs instalados
kubectl get crd | grep argoproj

# Verificar access entry criado automaticamente
aws eks list-access-entries --cluster-name meu-cluster

Próximos Passos

  • Avaliar se Secrets Manager é necessário ou se Kubernetes Secrets são suficientes para o seu caso de uso
  • Revisar as policies automáticas criadas pelo EKS no Access Entry e ajustar se necessário
  • Explorar o desafio de Cross-account para entender como a Capability Role é usada em deployments multi-conta

Desafio 5: ApplicationSet com Cluster Generator Dinâmico

Objetivo

Criar um ApplicationSet que descobre clusters automaticamente e faz deploy de uma aplicação em todos eles, sem precisar editar o manifesto quando novos clusters são adicionados.

Contexto

O workshop base usa o List Generator no ApplicationSet - você define uma lista estática de clusters no YAML. Funciona, mas não escala: cada novo cluster exige uma edição manual.

O Cluster Generator resolve isso. Ele consulta os clusters registrados no ArgoCD e gera Applications automaticamente para cada um. Você pode filtrar por labels para controlar quais clusters recebem qual aplicação.

No EKS Capabilities, os clusters são registrados via Kubernetes Secrets com a label argocd.argoproj.io/secret-type: cluster. O Cluster Generator lê esses secrets e usa os metadados como parâmetros no template.

Requisitos

  • Dois clusters registrados no ArgoCD com labels diferentes: env: staging e env: prod
  • ApplicationSet usando Cluster Generator que filtra por label env: staging
  • Deploy da aplicação guestbook apenas nos clusters de staging
  • Quando um novo cluster staging for registrado, o deploy deve acontecer automaticamente

Desafio

Crie os secrets de registro dos dois clusters e o ApplicationSet com Cluster Generator filtrado por label. Valide que apenas o cluster staging recebe a aplicação.

Dica: O Cluster Generator usa spec.generators[].clusters.selector.matchLabels para filtrar. As labels do secret do cluster ficam disponíveis como {{.metadata.labels.env}} no template.

💡 Ver solução

Solução

1. Registrar cluster staging

apiVersion: v1
kind: Secret
metadata:
  name: cluster-staging
  namespace: argocd
  labels:
    argocd.argoproj.io/secret-type: cluster
    env: staging
type: Opaque
stringData:
  name: staging
  server: arn:aws:eks:us-east-1:ACCOUNT_ID:cluster/meu-cluster-staging

2. Registrar cluster prod

apiVersion: v1
kind: Secret
metadata:
  name: cluster-prod
  namespace: argocd
  labels:
    argocd.argoproj.io/secret-type: cluster
    env: prod
type: Opaque
stringData:
  name: prod
  server: arn:aws:eks:us-east-1:ACCOUNT_ID:cluster/meu-cluster-prod

3. ApplicationSet com Cluster Generator

apiVersion: argoproj.io/v1alpha1
kind: ApplicationSet
metadata:
  name: guestbook-staging
  namespace: argocd
spec:
  goTemplate: true
  goTemplateOptions: ["missingkey=error"]
  generators:
  - clusters:
      selector:
        matchLabels:
          env: staging
  template:
    metadata:
      name: '{{.name}}-guestbook'
    spec:
      project: default
      source:
        repoURL: https://github.com/argoproj/argocd-example-apps.git
        path: guestbook
        targetRevision: HEAD
      destination:
        name: '{{.name}}'
        namespace: guestbook
      syncPolicy:
        automated:
          prune: true
          selfHeal: true
        syncOptions:
        - CreateNamespace=true

kubectl apply -f cluster-staging.yaml
kubectl apply -f cluster-prod.yaml
kubectl apply -f applicationset-staging.yaml

4. Validar

# Deve mostrar apenas a application do cluster staging
kubectl get applications -n argocd

# Adicionar um novo cluster staging e verificar deploy automático
# Basta criar outro secret com label env: staging

Por que isso importa

Com List Generator, adicionar 10 clusters = editar o YAML 10 vezes. Com Cluster Generator, você registra o cluster com a label correta e o deploy acontece automaticamente. Em ambientes com dezenas de clusters (multi-region, multi-account), essa diferença é crítica.

Próximos Passos

  • Usar Matrix Generator para combinar clusters com ambientes (dev/staging/prod)
  • Adicionar Git Generator para descobrir aplicações automaticamente por diretório no repositório
  • Implementar ApplicationSet com Pull Request Generator para preview environments

Desafio 6: Sync Windows + Break-glass

Objetivo

Configurar janelas de sincronização em um AppProject para bloquear deploys em produção durante o horário comercial, e executar um procedimento de break-glass para forçar um deploy de emergência fora da janela.

Contexto

Em ambientes de produção, deploys não controlados durante o horário de pico são um risco operacional. O ArgoCD resolve isso com Sync Windows - regras de tempo configuradas no AppProject que controlam quando aplicações podem ou não ser sincronizadas.

Existem dois tipos:

  • allow - sync só acontece dentro dessa janela
  • deny - sync é bloqueado durante essa janela

No self-managed ArgoCD, você poderia ajustar isso via argocd-cm ConfigMap. No EKS Capabilities, esse ConfigMap não é acessível - a única forma suportada é via spec.syncWindows no AppProject. Isso é um diferencial importante de operação.

O break-glass é o procedimento de emergência: forçar um sync mesmo com a janela bloqueada. No ArgoCD, isso é feito com a flag --bypass-sync-window no CLI, disponível apenas para usuários com role ADMIN.

Limitação importante: O sync timeout no EKS Capabilities é fixo em 120 segundos e não é configurável. Para workloads que demoram mais de 2 minutos para subir (ex: jobs de migração de banco), planeje estratégias alternativas como health checks customizados ou sync manual em etapas. Referência: Comparing EKS Capability for Argo CD to self-managed Argo CD

Requisitos

  • AppProject production com deny window de segunda a sexta, das 8h às 18h
  • Aplicação associada ao projeto production com sync automático habilitado
  • Simular um commit durante a janela bloqueada e observar o sync bloqueado na UI
  • Executar break-glass via CLI para forçar o deploy

Desafio

Configure o AppProject com a Sync Window e valide o comportamento de bloqueio. Em seguida, use o procedimento de break-glass para forçar o sync.

Dica: O cron da Sync Window usa o formato padrão. 0 8 * * 1-5 significa “às 8h de segunda a sexta”. A duração é em horas: 10h cobre das 8h às 18h.

💡 Ver solução

Solução

1. AppProject com Sync Window

apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: production
  namespace: argocd
spec:
  description: "Projeto de produção com janela de deploy controlada"
  sourceRepos:
  - '*'
  destinations:
  - namespace: '*'
    server: '*'
  sourceNamespaces:
  - argocd
  clusterResourceWhitelist:
  - group: '*'
    kind: '*'
  syncWindows:
  - kind: deny
    schedule: "0 8 * * 1-5"
    duration: 10h
    applications:
    - "*"
    namespaces:
    - "*"
    clusters:
    - "*"
    manualSync: false

kubectl apply -f production-project.yaml

2. Aplicação associada ao projeto production

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: minha-app-prod
  namespace: argocd
spec:
  project: production
  source:
    repoURL: https://github.com/argoproj/argocd-example-apps.git
    path: guestbook
    targetRevision: HEAD
  destination:
    name: in-cluster
    namespace: guestbook
  syncPolicy:
    automated:
      prune: true
      selfHeal: true

3. Validar bloqueio

Durante a janela de deny, qualquer commit no repositório não vai disparar sync automático. Na UI do ArgoCD, a aplicação aparece com status OutOfSync mas sem tentar sincronizar. Você verá a mensagem de sync window ativa.

# Verificar sync windows ativas
argocd proj windows list production

4. Break-glass - forçar sync fora da janela

# Requer role ADMIN no ArgoCD
argocd app sync minha-app-prod --bypass-sync-window

Na UI: Application > Sync > selecionar "Bypass Sync Window" (disponível apenas para admins).

5. Sync Window com janela de manutenção (allow)

Para permitir deploys apenas em janelas específicas, use kind: allow:

syncWindows:
- kind: allow
  schedule: "0 22 * * 5"   # sexta às 22h
  duration: 6h              # até sábado às 4h
  applications:
  - "*"

Comportamento com manualSync: true

Se manualSync: true na Sync Window, syncs manuais ainda são permitidos durante o bloqueio - apenas o sync automático é bloqueado. Útil para equipes que precisam de flexibilidade operacional sem abrir o break-glass completo.

Extra: Webhook para Sync Imediato

Por padrão, o ArgoCD EKS Capability faz polling dos repositórios a cada 6 minutos - diferente do self-managed que é 3 minutos. Para ambientes onde velocidade de feedback importa, configure webhooks para sync em segundos.

O endpoint do webhook no EKS Capabilities segue o padrão:

https://<seu-argocd-server>.eks-capabilities.<region>.amazonaws.com/api/webhook

Dica: A URL completa do seu ArgoCD está disponível no EKS Console em Clusters → Capabilities → Argo CD, ou via CLI:

aws eks describe-capability \
  --cluster-name meu-cluster \
  --capability-name meu-cluster-argocd \
  --query 'capability.configuration.argoCd.serverUrl' \
  --output text
💡 Ver solução

GitHub:

  1. No repositório → Settings → Webhooks → Add webhook
  2. Payload URL: https://<argocd-server>/api/webhook
  3. Content type: application/json
  4. Events: “Just the push event”

GitLab:

  1. No projeto → Settings → Webhooks
  2. URL: https://<argocd-server>/api/webhook
  3. Trigger: “Push events”

CodeCommit via EventBridge:

{
  "source": ["aws.codecommit"],
  "detail-type": ["CodeCommit Repository State Change"],
  "detail": {
    "event": ["referenceUpdated"],
    "repositoryName": ["meu-repo"]
  }
}

Target: API Destination apontando para https://<argocd-server>/api/webhook com método POST.

Validar:

Faça um commit e observe na UI do ArgoCD - a aplicação deve entrar em sync em segundos, não em até 6 minutos.

Webhooks complementam o polling - não o substituem. O ArgoCD continua fazendo polling como fallback caso uma notificação seja perdida.

Desafio 7: Cross-account Deployments via Access Entries

Objetivo

Configurar o ArgoCD EKS Capability em uma conta AWS (hub) para fazer deploy de aplicações em um cluster EKS em outra conta AWS (spoke), sem usar IRSA nem role chaining.

Contexto

Em arquiteturas multi-conta, o padrão tradicional para o ArgoCD self-managed acessar clusters em outras contas envolve IRSA, trust policies entre contas, e role assumption chains - configuração complexa e propensa a erros.

O EKS Capabilities simplifica radicalmente isso. Como o ArgoCD roda no control plane da AWS, o acesso cross-account é feito diretamente via EKS Access Entries: você adiciona o ARN da IAM Capability Role da conta hub como principal no cluster da conta spoke. Sem VPC peering, sem Transit Gateway, sem role chaining.

O ArgoCD gerencia a conectividade automaticamente - inclusive para clusters com API endpoint privado.

Requisitos

  • Conta A (hub): cluster EKS com ArgoCD Capability habilitado
  • Conta B (spoke): cluster EKS alvo do deploy
  • Access Entry no cluster spoke autorizando a Capability Role da conta hub
  • Cluster spoke registrado no ArgoCD via Secret com o ARN do cluster
  • Deploy de uma aplicação no cluster spoke validado via UI

Desafio

Configure o Access Entry na conta spoke e registre o cluster no ArgoCD da conta hub. Faça o deploy de uma aplicação e valide que ela está rodando no cluster da conta B.

Dica: O Access Entry usa o ARN da Capability Role da conta hub como principal. Para produção, evite AmazonEKSClusterAdminPolicy - crie uma policy customizada com apenas as permissões necessárias para o ArgoCD deployar nos namespaces alvo.

💡 Ver solução

Solução

1. Obter o ARN da Capability Role (conta hub)

# Na conta hub
aws iam get-role --role-name ArgoCD-Capability-Role \
  --query 'Role.Arn' --output text
# Resultado: arn:aws:iam::HUB_ACCOUNT_ID:role/ArgoCD-Capability-Role

2. Criar Access Entry no cluster spoke (conta B)

# Na conta spoke (B)
aws eks create-access-entry \
  --cluster-name meu-cluster-spoke \
  --principal-arn arn:aws:iam::HUB_ACCOUNT_ID:role/ArgoCD-Capability-Role \
  --type STANDARD

# Associar policy de admin (simplificado para lab)
aws eks associate-access-policy \
  --cluster-name meu-cluster-spoke \
  --principal-arn arn:aws:iam::HUB_ACCOUNT_ID:role/ArgoCD-Capability-Role \
  --policy-arn arn:aws:eks::aws:cluster-access-policy/AmazonEKSClusterAdminPolicy \
  --access-scope type=cluster

3. Registrar cluster spoke no ArgoCD (conta hub)

# Obter ARN do cluster spoke
SPOKE_ARN=$(aws eks describe-cluster \
  --name meu-cluster-spoke \
  --profile conta-spoke \
  --query 'cluster.arn' --output text)

apiVersion: v1
kind: Secret
metadata:
  name: cluster-spoke-contab
  namespace: argocd
  labels:
    argocd.argoproj.io/secret-type: cluster
    env: prod
    account: spoke
type: Opaque
stringData:
  name: spoke-prod
  server: arn:aws:eks:us-east-1:SPOKE_ACCOUNT_ID:cluster/meu-cluster-spoke

kubectl apply -f cluster-spoke.yaml

4. Validar registro

# Na UI: Settings > Clusters - o cluster spoke deve aparecer como Connected
# Via CLI:
argocd cluster list

5. Deploy de aplicação no cluster spoke

apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: app-cross-account
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/argoproj/argocd-example-apps.git
    path: guestbook
    targetRevision: HEAD
  destination:
    name: spoke-prod
    namespace: guestbook
  syncPolicy:
    automated: {}
    syncOptions:
    - CreateNamespace=true

Por que não precisa de VPC peering

O ArgoCD EKS Capability roda no control plane da AWS, não nos seus worker nodes. A AWS gerencia a conectividade entre o serviço e os clusters alvo - incluindo clusters com API endpoint 100% privado. Isso elimina toda a complexidade de networking que seria necessária com ArgoCD self-managed.

Produção: least-privilege no Access Entry

Em vez de AmazonEKSClusterAdminPolicy, crie um ClusterRole restrito:

apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: argocd-deploy
rules:
- apiGroups: ["apps", ""]
  resources: ["deployments", "services", "configmaps", "namespaces"]
  verbs: ["get", "list", "watch", "create", "update", "patch", "delete"]

Próximos Passos

  • Usar AWS Organizations para automatizar a criação de Access Entries em novos clusters spoke
  • Combinar com o desafio de Fleet Management para ver como cross-account funciona em escala

Desafio 8: Troubleshooting - Drift, Sync Failure e Health Degraded

Objetivo

Diagnosticar e resolver três cenários reais de falha no ArgoCD EKS Capabilities: drift manual no cluster, sync failure por permissão insuficiente, e aplicação com health degraded.

Contexto

O ArgoCD detecta e corrige automaticamente desvios entre o estado desejado (Git) e o estado real (cluster). Mas quando algo falha, saber onde olhar é a diferença entre resolver em 5 minutos ou passar horas no escuro.

No EKS Capabilities, algumas ferramentas de debug do self-managed não estão disponíveis - você não tem acesso direto aos logs do ArgoCD controller, não pode editar argocd-cm, e o sync timeout é fixo em 120 segundos. O debug é feito via UI do EKS Console, kubectl no cluster alvo, e os eventos do Kubernetes.

Referência: Comparing EKS Capability for Argo CD to self-managed Argo CD - lista completa de features não disponíveis no managed capability.

Os três cenários abaixo são independentes. Tente resolver cada um antes de abrir a solução.

Cenário 1: Drift Detection

Situação: Uma aplicação está Synced e Healthy. Um desenvolvedor faz uma mudança manual direta no cluster (kubectl edit deployment). O que acontece e como reverter?

Dica: O ArgoCD EKS Capability faz polling a cada 6 minutos por padrão. Se você configurou webhook no desafio anterior, a detecção é imediata.

💡 Ver solução

O que acontece: O ArgoCD detecta o drift no próximo ciclo de polling e muda a aplicação para OutOfSync.

Como ver o drift na UI:

  • Application > App Diff - mostra exatamente o que mudou no cluster vs Git
  • Resources com ícone de alerta indicam divergência

Reverter o drift:

Se selfHeal: true estiver no syncPolicy, o ArgoCD reverte automaticamente. Se não:

# Forçar sync para reverter ao estado do Git
argocd app sync minha-app --force

Prevenir drift em produção:

syncPolicy:
  automated:
    prune: true
    selfHeal: true

Cenário 2: Sync Failure por Permissão

Situação: Você cria uma Application que tenta criar um ClusterRole. O sync falha com erro de permissão. O AppProject está configurado com clusterResourceWhitelist vazio.

Dica: A mensagem de erro exata aparece na UI do ArgoCD ao expandir o recurso com falha em Sync Status.

💡 Ver solução

Diagnóstico:

# Ver eventos de sync
kubectl get events -n argocd --sort-by='.lastTimestamp'

# Ver detalhes da application
kubectl describe application minha-app -n argocd

Causa raiz: clusterResourceWhitelist: [] bloqueia recursos cluster-scoped (ClusterRole, ClusterRoleBinding, Namespace, etc.).

Correção no AppProject:

spec:
  clusterResourceWhitelist:
  - group: "rbac.authorization.k8s.io"
    kind: "ClusterRole"
  - group: "rbac.authorization.k8s.io"
    kind: "ClusterRoleBinding"

kubectl apply -f project-corrigido.yaml
argocd app sync minha-app

Cenário 3: Health Degraded

Situação: Uma Application está Synced mas Degraded. O deployment foi aplicado mas os pods não sobem. Como diagnosticar via ArgoCD e via kubectl?

Dica: Synced significa que o ArgoCD aplicou o manifesto com sucesso. Degraded significa que o Kubernetes não conseguiu subir os pods - são problemas diferentes.

💡 Ver solução

Diagnóstico na UI do ArgoCD:

  • Application > clicar no recurso Deployment > aba Events
  • Pods com ImagePullBackOff, CrashLoopBackOff, Pending aparecem em vermelho

Diagnóstico via kubectl:

kubectl get pods -n meu-namespace
kubectl describe pod NOME_DO_POD -n meu-namespace
kubectl logs NOME_DO_POD -n meu-namespace --previous

Causas comuns:

StatusCausa provávelCorreção
ImagePullBackOffImagem não existe ou sem permissão no ECRCorrigir tag no Git ou adicionar permissão ECR na node role
CrashLoopBackOffAplicação crashando na inicializaçãoVer logs com --previous, corrigir config/env vars
PendingSem recursos no clusterEscalar node group ou ajustar requests/limits
OOMKilledLimite de memória atingidoAumentar resources.limits.memory no manifesto

Diferença importante no EKS Capabilities:

No self-managed você teria acesso direto aos logs do argocd-application-controller. No EKS Capabilities o debug é via:

  • UI do EKS Console
  • kubectl describe application e eventos do Kubernetes
  • CloudTrail para auditoria das chamadas de API do ArgoCD

Próximos Passos

  • Implementar health checks customizados para CRDs e recursos não-padrão
  • Integrar CloudTrail com CloudWatch para alertas em sync failures recorrentes
  • Explorar o desafio de Fleet Management para ver como troubleshooting escala em ambientes multi-cluster

Desafio 9: Fleet Management com kro + ACK + ArgoCD

Objetivo

Implementar uma arquitetura hub-spoke para gerenciamento de fleet de clusters EKS usando as três tecnologias juntas: kro para orquestrar a criação dos clusters, ACK para provisionar os recursos AWS, e ArgoCD EKS Capability para bootstrapar e gerenciar os addons via GitOps.

Contexto

Este é o desafio final - ele integra tudo que foi visto nos desafios anteriores numa arquitetura de produção real.

O exemplo oficial do kro demonstra exatamente esse padrão: um cluster de gerenciamento (hub) com as três EKS Capabilities habilitadas provisiona e bootstrapa clusters de workload (spokes) de forma totalmente declarativa e GitOps.

Pré-requisitos

  • Conta AWS de gerenciamento (hub) com AWS Identity Center configurado
  • Uma ou mais contas spoke (pode reusar a mesma conta para testes)
  • GitHub account com token para o repositório GitOps
  • Terraform CLI, AWS CLI v2.32.27+, ArgoCD CLI, GitHub CLI

Fase 1: Preparar o repositório GitOps

Configure as variáveis de ambiente, clone o repositório do kro, crie seu repositório GitOps privado no GitHub e popule com os arquivos do exemplo.

Dica: O WORKING_REPO é referenciado em configs do Terraform e GitOps - mantenha o nome padrão eks-cluster-mgmt.

💡 Ver solução
export KRO_REPO_URL="https://github.com/kubernetes-sigs/kro.git"
export WORKING_REPO="eks-cluster-mgmt"
export MGMT_ACCOUNT_ID=$(aws sts get-caller-identity --output text --query Account)
export AWS_REGION="us-east-1"
export WORKSPACE_PATH="$HOME"
export GITHUB_ORG_NAME="seu-usuario-github"

git clone $KRO_REPO_URL $WORKSPACE_PATH/kro
gh repo create $WORKING_REPO --private
gh repo clone $WORKING_REPO $WORKSPACE_PATH/$WORKING_REPO
cp -r $WORKSPACE_PATH/kro/examples/aws/eks-cluster-mgmt/* $WORKSPACE_PATH/$WORKING_REPO/

Edite terraform/hub/terraform.tfvars com seu git_org_name e accounts_ids (use o ID da conta de gerenciamento se não tiver contas spoke separadas).

Se quiser usar múltiplas contas spoke, edite também:

# accounts_ids no tfvars aceita lista de IDs das contas spoke
code $WORKSPACE_PATH/$WORKING_REPO/terraform/hub/terraform.tfvars

Commit e push inicial:

cd $WORKSPACE_PATH/$WORKING_REPO
git add . && git commit -s -m "initial commit" && git push

Fase 2: Provisionar o cluster hub com Terraform

Aplique o Terraform para criar o cluster hub com as IAM Roles necessárias para cada Capability. O Terraform não cria as Capabilities - isso é feito na próxima fase via CLI.

Dica: O install.sh executa terraform init, plan e apply. Revise o plan antes de confirmar - ele cria VPC, EKS cluster, IAM roles e mais.

💡 Ver solução
cd $WORKSPACE_PATH/$WORKING_REPO/terraform/hub
./install.sh

# Exportar outputs para as próximas fases
export CLUSTER_NAME=$(terraform output -raw cluster_name)
export ACK_CONTROLLER_ROLE_ARN=$(terraform output -raw ack_controller_role_arn)
export KRO_CONTROLLER_ROLE_ARN=$(terraform output -raw kro_controller_role_arn)
export ARGOCD_CONTROLLER_ROLE_ARN=$(terraform output -raw argocd_controller_role_arn)

echo "Cluster: $CLUSTER_NAME"
echo "ACK Role: $ACK_CONTROLLER_ROLE_ARN"
echo "kro Role: $KRO_CONTROLLER_ROLE_ARN"
echo "ArgoCD Role: $ARGOCD_CONTROLLER_ROLE_ARN"

Configurar kubectl:

aws eks update-kubeconfig --name $CLUSTER_NAME --region $AWS_REGION
kubectl get nodes

Fase 3: Criar as três EKS Capabilities

Habilite ACK, kro e ArgoCD como EKS Capabilities no cluster hub. Cada uma requer a IAM Role criada pelo Terraform na fase anterior.

Dica: O ArgoCD requer AWS Identity Center configurado na conta. Você precisará do ARN da instância IDC e do ID do usuário que terá acesso admin ao ArgoCD.

💡 Ver solução
# ACK
aws eks create-capability \
  --region ${AWS_REGION} \
  --cluster-name ${CLUSTER_NAME} \
  --capability-name ${CLUSTER_NAME}-ack \
  --type ACK \
  --role-arn ${ACK_CONTROLLER_ROLE_ARN} \
  --delete-propagation-policy RETAIN

# kro
aws eks create-capability \
  --region ${AWS_REGION} \
  --cluster-name ${CLUSTER_NAME} \
  --capability-name ${CLUSTER_NAME}-kro \
  --type KRO \
  --role-arn ${KRO_CONTROLLER_ROLE_ARN} \
  --delete-propagation-policy RETAIN

# ArgoCD - obter dados do Identity Center
export IDC_INSTANCE_ARN='arn:aws:sso:::instance/ssoins-XXXXXXXX'
export IDC_USER_ID='XXXXXXXX-XXXX-XXXX-XXXX-XXXXXXXXXXXX'
export IDC_REGION='us-east-1'

aws eks create-capability \
  --region ${AWS_REGION} \
  --cluster-name ${CLUSTER_NAME} \
  --capability-name ${CLUSTER_NAME}-argocd \
  --type ARGOCD \
  --role-arn ${ARGOCD_CONTROLLER_ROLE_ARN} \
  --delete-propagation-policy RETAIN \
  --configuration '{
    "argoCd": {
      "awsIdc": {
        "idcInstanceArn": "'${IDC_INSTANCE_ARN}'",
        "idcRegion": "'${IDC_REGION}'"
      },
      "rbacRoleMappings": [{
        "role": "ADMIN",
        "identities": [{
          "id": "'${IDC_USER_ID}'",
          "type": "SSO_USER"
        }]
      }]
    }
  }'

Aguardar todas as Capabilities ficarem ACTIVE:

for cap in ack kro argocd; do
  echo -n "${cap}: "
  aws eks describe-capability \
    --region ${AWS_REGION} \
    --cluster-name ${CLUSTER_NAME} \
    --capability-name ${CLUSTER_NAME}-${cap} \
    --query 'capability.status' --output text
done

Fase 4: Configurar ArgoCD e bootstrapar o hub

Obtenha a URL do ArgoCD, gere um token de acesso e registre o repositório GitOps. Em seguida, aplique o App of Apps que inicia toda a automação GitOps.

Dica: O token é gerado na UI do ArgoCD em Settings → Accounts → admin → Generate New Token. A URL do ArgoCD está disponível no EKS Console em Clusters → Capabilities → Argo CD.

💡 Ver solução
# Obter URL do ArgoCD
export ARGOCD_SERVER=$(aws eks describe-capability \
  --cluster-name ${CLUSTER_NAME} \
  --capability-name ${CLUSTER_NAME}-argocd \
  --query 'capability.configuration.argoCd.serverUrl' \
  --output text --region ${AWS_REGION})

export ARGOCD_SERVER=${ARGOCD_SERVER#https://}
export ARGOCD_OPTS="--grpc-web"

echo "ArgoCD URL: https://${ARGOCD_SERVER}"

Gere o token na UI e configure:

export ARGOCD_AUTH_TOKEN="<token-gerado-na-ui>"
export GITHUB_TOKEN="<seu-github-token>"

# Registrar repositório GitOps
argocd repo add https://github.com/$GITHUB_ORG_NAME/$WORKING_REPO.git \
  --username $GITHUB_ORG_NAME \
  --password $GITHUB_TOKEN \
  --upsert --name github

# Aplicar App of Apps - inicia toda a automação
kubectl apply -f $WORKSPACE_PATH/$WORKING_REPO/terraform/hub/bootstrap/applicationsets.yaml

# Verificar ApplicationSets criados
kubectl get applicationsets -n argocd

Fase 5: Provisionar cluster spoke via kro

Configure as contas spoke com as IAM Roles necessárias para o ACK cross-account, declare o cluster spoke no repositório GitOps e observe o kro + ACK provisionando tudo automaticamente.

Dica: Mesmo usando uma única conta, o script create_ack_workload_roles.sh precisa ser executado - ele cria as roles que o ACK usa para provisionar recursos na conta spoke.

💡 Ver solução

Configurar conta spoke:

export AWS_PROFILE=spoke_account1
cd $WORKSPACE_PATH/$WORKING_REPO/scripts
./create_ack_workload_roles.sh

Declarar o cluster spoke no GitOps:

Edite fleet/kro-values/tenants/tenant1/kro-clusters/values.yaml:

workload-cluster1:
  managementAccountId: "MGMT_ACCOUNT_ID"
  accountId: "SPOKE_ACCOUNT_ID"
  tenant: "tenant1"
  k8sVersion: "1.32"
  workloads: "true"
  gitops:
    addonsRepoUrl: "https://github.com/SEU_USUARIO/eks-cluster-mgmt"
    fleetRepoUrl: "https://github.com/SEU_USUARIO/eks-cluster-mgmt"
    platformRepoUrl: "https://github.com/SEU_USUARIO/eks-cluster-mgmt"
    workloadRepoUrl: "https://github.com/SEU_USUARIO/eks-cluster-mgmt"

cd $WORKSPACE_PATH/$WORKING_REPO
git add . && git commit -s -m "add workload-cluster1" && git push

Acompanhar provisionamento:

# kro orquestrando a criação
kubectl get EksClusterwithvpcs -A

# ACK criando recursos AWS
kubectl get vpcs.ec2.services.k8s.aws -A
kubectl get clusters.eks.services.k8s.aws -A

Quando STATE=ACTIVE, conectar ao spoke e validar addons:

export AWS_PROFILE=spoke_account1
aws eks update-kubeconfig --name workload-cluster1 --region us-east-1
kubectl get pods -A

Conclusão

Você implementou uma plataforma completa de fleet management onde um único cluster hub, com três EKS Capabilities gerenciadas pela AWS, provisiona e bootstrapa clusters de workload de forma totalmente declarativa.

O ciclo completo é GitOps do início ao fim: um git push com a declaração de um novo cluster dispara kro para orquestrar, ACK para provisionar na AWS, e ArgoCD para instalar os addons - sem nenhuma intervenção manual após a configuração inicial.

Essa é a arquitetura que times de Platform Engineering usam para escalar de 5 para 50 clusters sem aumentar a equipe.

Recursos Adicionais

Problemas comuns que clientes encontram nessa arquitetura:

  • Troubleshoot issues with ACK capabilities - Capability ACTIVE mas recursos não sendo criados, recursos criados na AWS mas não aparecendo no Kubernetes, problemas de cross-account
  • Additional Kubernetes permissions for EKS Capabilities - Permissões Kubernetes adicionais além das concedidas automaticamente pelo Access Entry, necessárias para casos como ACK lendo Secrets ou kro criando recursos customizados
